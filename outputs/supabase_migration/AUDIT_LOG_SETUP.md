# 監査ログの設定

1. Supabase のプロジェクト画面で **SQL Editor** を開きます。
2. `create_audit_logs.sql` の内容を全部貼り付けて **Run** を押します。
3. 在庫管理システムを再読み込みし、メニューの **データ管理 → 監査ログ** を開きます。

SQL の実行後に行ったデータ変更から記録を開始します。導入前の操作履歴は復元できません。
初めて開いたときに「該当する監査ログはありません」と表示されるのは正常です。
通常の操作でデータを保存すると、監査ログの「更新」で確認できます。

## 記録される内容

- 日時（画面は日本時間）、操作アカウント、対象とID、追加・修正・削除の区分。
- 変更前・変更後のデータ。削除されたデータも、削除前の内容を保持します。
- 対象は、資産・品目・分類・入出庫・取引先・担当者・発注・棚卸し・棚卸し明細・年度在庫。
- 棚卸し調整、年度更新、バックアップ復元による各行の変更も記録します。
- 同じ値を再保存しただけの場合や、失敗して取り消された変更は記録しません。

操作アカウントはログインに使った Supabase アカウントです。入力担当者は入出庫データの
担当者欄として別に保存されます。アカウントを共用している場合、監査ログだけでは
実際に操作した個人を区別できません。管理画面や自動処理からの変更は、ログイン情報が
ない場合「DB管理・自動処理」と表示します。

## 保存の扱い

監査ログは `invent_audit_logs` に保存され、アプリには閲覧権限だけを与えます。
ログを追加するのはデータベースのトリガーです。データの変更とログの追加を
同じトランザクションで確定するため、ログの保存が失敗した場合はデータの変更も失敗します。

ログは自動削除しません。アプリの通常復元・完全復元の対象にも含めないため、
バックアップ復元によって以前の監査ログが消えたり書き換わったりしません。
既存のバックアップJSONには監査ログは含まれません。
データベース管理者はSQLで変更できるため、管理者にも変更できない保管庫ではありません。

この機能はデータ行の追加・修正・削除を対象にします。ログイン、閲覧、印刷、
バックアップファイルの保存・ダウンロード、テーブルの削除・TRUNCATE・構造変更は対象外です。

SQL は再実行できます。ログは保持されます。対象テーブルのうち未作成のものはスキップするため、
後から新しい対象テーブルを作った場合は、このSQLをもう一度実行してください。

## 検証

`node --test tests/audit.test.mjs` で日付境界・ページ切り替え・変更内容表示を検証できます。
SQLの検証は本番ではなく、一時的な PostgreSQL（PGlite）上で行いました。
`INVENT_AUDIT_PGLITE_PATH` に PGlite の `dist/index.js` の絶対パスを設定し、
`node --test tests/audit.test.mjs tests/audit-migration.test.mjs` を実行します。

方式の参考: [Supabase のトリガー](https://supabase.com/docs/guides/database/postgres/triggers)、
[Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)。
